# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Project

BaselithCore — a modular orchestration engine for production-grade agentic AI. Python 3.12+ (no upper cap; forward-compatible with newer CPython releases as upstream deps catch up), packaged as `baselith-core` (PyPI). FastAPI-based backend with an optional plugin ecosystem.

## Sacred Core rule (architectural invariant)

> The `core/` directory contains **only** domain-agnostic logic (orchestration, infrastructure, utilities). Domain-specific logic, external integrations, and business features **must** live under `plugins/`.

This is enforced by [scripts/check_architecture_boundaries.py](scripts/check_architecture_boundaries.py):

- It freezes the current set of legacy domain modules under `core/agents/`, `core/doc_sources/`, `core/goals/`, `core/routers/`, `core/scraper/` via a `LEGACY_CORE_FILE_ALLOWLIST`. Do not add new files to these frozen prefixes — create a plugin instead.
- Any new `core -> plugins` imports are blocked (only existing compatibility shims are grandfathered).

When making changes, prefer extending via a plugin under `plugins/<name>/` rather than touching `core/`.

## Companion open-core repo — keep `core/` aligned

This repo (`baselithcore-enterprise`) is the **superset**: it carries the full plugin ecosystem (`auth`, etc.). The sibling checkout [`baselithcore-prod`](../baselithcore-prod) (remote `github.com/baselithcore/baselithcore`, the public/general project) ships the **same `core/`** but **none of the enterprise plugins** (no `auth`, etc.).

> **Whenever a change is a *general/framework* implementation — i.e. it touches `core/` (or any shared, domain-agnostic machinery) — evaluate mirroring it into `baselithcore-prod`, *both the code AND its documentation*, to keep the general project aligned.** This is the default for core changes; skip it only when the change is enterprise-specific. Code and docs are mirrored together, not as separate optional steps.

How to apply it:

- **Scope = `core/` only.** Sync the `core/` (and other shared, non-plugin) edits; do **not** port `plugins/<enterprise-only>/` changes — those plugins don't exist in `baselithcore-prod`. A new core symbol/seam (e.g. a `core.context` helper) is exactly what should be mirrored, even if prod has no consumer yet, so the two `core/` trees never drift.
- **Diff before porting.** `diff <prod>/core/<file> <ent>/core/<file>` first. A clean diff (only your additions, no other divergence) ⇒ safe 1:1 port. If prod's `core/` has diverged independently, reconcile rather than overwrite.
- **Verify in prod after porting**: the two `core/` files end byte-identical, prod `py_compile`s, and `python scripts/check_architecture_boundaries.py` stays green in the prod checkout.
- **Docs are part of the mirror — mandatory when the change needs it, not optional.** When a synced core/framework change adds or alters behaviour that the prod `mkdocs-site` documents (or *should* document), update the relevant page(s) in the same pass — find them under `baselithcore-prod/mkdocs-site/docs/` (e.g. `advanced/multi-tenancy.md`, `core-modules/*`, `plugins/*`). Document only the **framework** mechanism (prod has no enterprise plugins, so never reference enterprise-plugin UIs/routes like the `auth` console — describe the seam/API, not the auth-admin surface). If prod's docs have diverged or already cover the area, extend them in place rather than overwriting.
- Commit/push to prod only when the user asks; otherwise leave the prod working tree staged for review.

## Architecture big picture

Entry point [backend.py](backend.py) calls `core.api.factory.create_app()` to build the FastAPI app. App and core settings come from Pydantic-settings via `core.config.get_app_config()` / `get_core_config()`.

### Core layers (all under [core/](core/))

- **[orchestration/](core/orchestration/)** — top-level orchestrator, intent classifier, router, adaptive/parallel execution, flow handlers. The orchestrator is the heart of the agentic loop. Runtime primitives: `LoopBudget` ([limits.py](core/orchestration/limits.py)), `AgentContract` ([contract.py](core/orchestration/contract.py)), `AutonomyPolicy` ([autonomy.py](core/orchestration/autonomy.py)), `TaskClassifier` ([task_classifier.py](core/orchestration/task_classifier.py)).
- **[memory/](core/memory/)** — multilayer memory hierarchy STM → MTM → LTM with consolidation; plus `Scratchpad` ([scratchpad.py](core/memory/scratchpad.py)) for agent-written section memory and `BM25Index` + `HybridSearcher` ([hybrid_search.py](core/memory/hybrid_search.py)) for keyword/dense RRF fusion.
- **[storage/](core/storage/)** & **[db/](core/db/)** — relational (Postgres via `psycopg`/Alembic migrations in [migrations/](migrations/)) and vector (Qdrant) backends; also [cache/](core/cache/) (Redis).
- **[reasoning/](core/reasoning/)**, **[world_model/](core/world_model/)**, **[swarm/](core/swarm/)**, **[planning/](core/planning/)**, **[meta/](core/meta/)** — cognitive subsystems (MCTS, Tree-of-Thoughts, auction protocols, multi-persona internal debate). Generator-vs-Challenger adversarial protocol lives in [meta/generator_challenger.py](core/meta/generator_challenger.py).
- **[plugins/](core/plugins/)** — the plugin registry/loader/hotreload framework (`agent_plugin.py`, `router_plugin.py`, `graph_plugin.py`, `loader.py`, `registry.py`). This is the *machinery* that loads external plugins. Shared envelopes for tools/skills: `SkillResult` + `ok`/`fail`/`partial` ([result.py](core/plugins/result.py)). Declarative `SKILL.md` catalog with progressive disclosure: `DeclarativeSkillLoader` ([declarative.py](core/plugins/declarative.py)).
- **[api/](core/api/)**, **[routers/](core/routers/)**, **[middleware/](core/middleware/)**, **[auth/](core/auth/)** — FastAPI surface.
- **[mcp/](core/mcp/)** — native Model Context Protocol support. Companion: A2A peer-discovery ([a2a/](core/a2a/)) plus an A2UI blueprint schema ([a2a/a2ui.py](core/a2a/a2ui.py)) that restricts agent-emitted UI to a whitelisted component tree.
- **[llm layer]** spans `core/models/`, `core/chat/` — multi-provider (Anthropic, OpenAI, Ollama, HuggingFace). Portability primitives: pricing table ([models/pricing.py](core/models/pricing.py)), `ModelRouter` ([models/routing.py](core/models/routing.py)), `FallbackChain` ([models/fallback.py](core/models/fallback.py)). `AgentState` ([chat/agent_state.py](core/chat/agent_state.py)) carries `iteration_count`, `retry_count`, `cost_usd`, `scratchpad_ref`, `trajectory`.
- **[evaluation/](core/evaluation/)** — trajectory-aware case evaluation ([trajectory.py](core/evaluation/trajectory.py)) and CI replay runner ([regression_runner.py](core/evaluation/regression_runner.py)).
- **[personas/](core/personas/)** — persona registry plus a task-indexed few-shot example library ([few_shot.py](core/personas/few_shot.py)).
- **[world_model/](core/world_model/)** — risk/rollback/simulation; signed-mandate chain for agent-initiated commerce in [mandates.py](core/world_model/mandates.py) (Ed25519, intent → cart verification).
- **[resilience/](core/resilience/)** — circuit breakers, retries, etc. Subject to a **strict mypy gate** via `scripts/check_core_resilience_typing.py`.
- **[observability/](core/observability/)** — structlog + OpenTelemetry + Prometheus + Sentry.

A module-by-module status and integration map for the agentic runtime is maintained in [docs/architecture/agentic_modules.md](docs/architecture/agentic_modules.md) — read it before wiring a new handler into the loop.

### Plugins ([plugins/](plugins/))

Each plugin is a self-contained directory (see `plugins/example-plugin/` for the reference structure) with its own `manifest.yaml|yml|json` (declared in `pyproject.toml` package-data). The registry injects handlers into the orchestrator and routers into the API gateway at load time.

Official plugins listed under [plugins/](plugins/) (e.g. `api_routers`, `baselithbot`, `browser_agent`, `coding_agent`, `document_sources`, `goals`, `reasoning_agent`, `web_scraper`) are covered by `scripts/check_official_plugin_typing.py` — a focused strict-typing gate that runs in CI.

`baselithbot` is the flagship autonomous multi-channel agent plugin (OpenClaw-style skills, stealth browsing, desktop/computer-use, canvas A2UI, voice, cron, MCP). It bundles a 20-tab React dashboard under `plugins/baselithbot/ui/` — `npm run build` must produce `ui/dist/` before wheel packaging (only `ui/dist/**` ships; `ui/src/` and `ui/node_modules/` are excluded via `[tool.setuptools.exclude-package-data]`).

**Repository model — dual-hosted, single-sourced.** `plugins/baselithbot/` in this monorepo is the source of truth. The standalone marketplace repo [`plugin-baselithbot`](https://github.com/baselithcore/plugin-baselithbot) is **output-only**: populated on each release via `git subtree split -P plugins/baselithbot` and force-pushed. All edits (including hotfixes) land here first, then the subtree is split and pushed. Never commit directly to the standalone repo — any non-subtree commit there will be overwritten. See [plugins/baselithbot/docs/publishing.md](plugins/baselithbot/docs/publishing.md) §8 for the full release flow.

## Conventions

- **Python 3.12+** with rigorous type hints; Pydantic for configs/models; async/await for all I/O. Use modern syntax: PEP 604 unions (`X | Y`), PEP 695 generics where applicable, `tomllib` (stdlib).
- **File size cap: 500 LOC — HARD LIMIT, NON-NEGOTIABLE.** Applies to every source file — `.py` under `core/`, `plugins/`, `tests/`, `scripts/`, **and** frontend source (`.ts`, `.tsx`, `.js`, `.jsx`, `.vue`) under any plugin `ui/src/` (excluding generated/build output and `node_modules/`). No exceptions, no "just this once", no waivers. Counts physical lines including blanks and comments. **This applies from the very first commit of any new implementation — design modular from day one, never write a monolith planning to "split later".** Any file approaching the cap must be split *before* the PR, not after. Refactor strategies (in order of preference): (1) extract cohesive submodules into a package (`foo.py` → `foo/{__init__.py, _core.py, _helpers.py, _types.py}`; for frontend, split a fat component into `Component/{index.tsx, hooks.ts, parts/*.tsx, types.ts}`), (2) move pure helpers to a sibling `utils.py` / `types.py` (or `utils.ts` / `types.ts`), (3) split agents/routers/handlers/components along responsibility seams (parsing vs. orchestration vs. I/O vs. persistence; for UI: presentation vs. state vs. data-fetching). New features land as multiple small modules from day one — never as a single monolithic file with a "TODO: split later". CI/pre-commit MUST reject any file over 500 LOC; if the check is missing locally, run `find core plugins -name '*.py' -exec wc -l {} + | awk '$1 > 500'` (and the equivalent over `ui/src` for frontend) before pushing.
- Every module has an `__init__.py` with explicit exports.
- Google-style docstrings for public APIs.
- Mock LLMs and DBs in unit tests.
- **Secrets**: wrap every credential in `pydantic.SecretStr` (or `Set[SecretStr]` for collections). Direct `str` storage of API keys, tokens, or passwords leaks via `repr()`/Sentry frames and is rejected at review.
- **Middleware**: write new HTTP middleware as **pure ASGI** (`async def __call__(scope, receive, send)`), never `BaseHTTPMiddleware` — the latter wraps every request in an extra anyio task and breaks streaming/cancellation.
- **Plugin integrity**: a manifest may declare `integrity_sha256`. The loader verifies it via `core.plugins.integrity.verify_plugin_integrity` before `exec_module`. Set `BASELITH_REQUIRE_SIGNED_PLUGINS=true` to reject unsigned plugins.
- **Browser SSRF**: `BrowserAgent` blocks loopback/private/link-local/multicast hosts and non-`http(s)` schemes. Override only via `BASELITH_BROWSER_ALLOW_INTERNAL=true` for trusted local development.
- **Frontend stack**: a plugin UI may be built **either** with **React + Vite** (`npm`, as `baselithbot/ui/` does) **or** with **Next.js** (`pnpm`) following modern best practices (App Router, Server Components, etc.). Pick per plugin; both are first-class. Whichever you choose, the build must emit static/packageable output (Vite → `ui/dist/`; Next.js → its build/export dir) so only built artifacts ship in the wheel — `ui/src/` and `ui/node_modules/` stay excluded via `[tool.setuptools.exclude-package-data]`. The 500 LOC cap applies to frontend source regardless of framework.
- **i18n (multilingual) — mandatory for every new plugin from now on.** Every new plugin ships **internationalized by default with English (`en`, default/fallback) and Italian (`it`)** — both locales complete at launch, no partial coverage, no hardcoded user-facing strings. Use a standard **i18n** layer, not inline literals:
    - **Frontend** (React/Vite or Next.js): use a real i18n library (e.g. `react-i18next` / `i18next`, or `next-intl` for Next.js). All user-facing copy comes from per-locale message catalogs (`ui/src/locales/{en,it}/*.json` or framework equivalent) keyed by id — never literal strings in JSX. Provide a language switcher and detect/persist the user's locale; fall back to `en` on missing keys.
    - **Backend** (Python): any user-facing text the API returns (error messages, labels, notifications, report headings) is localized — resolve the locale from the `Accept-Language` header (or an explicit locale param/setting) and look up messages from per-locale catalogs (e.g. `locales/{en,it}.json` / `.po`), defaulting to `en`. No hardcoded English in responses meant for end users.
    - Keep `en` and `it` catalogs in sync — adding a key in one locale requires adding it in the other in the same PR. Catalog files count toward the 500 LOC cap like any source file; split large catalogs by feature/namespace.
    - Existing plugins are grandfathered, but any **new** plugin (and any new user-facing surface added to an existing one) must follow this from its first commit — design the i18n layer in from day one, never retrofit "later".
- **Core reuse — survey before you build.** When developing a new plugin in response to a user request, you **must** first survey every relevant capability the framework `core/` already offers and reuse what fits, rather than reimplementing it inside the plugin. Before writing plugin code, map the request against the core subsystems (orchestration, memory STM/MTM/LTM + scratchpad + hybrid search, storage/db/cache, reasoning/world_model/swarm/planning/meta, the plugin framework + `SkillResult` envelopes, mcp/a2a, the llm layer — providers/pricing/`ModelRouter`/`FallbackChain`/`AgentState`, evaluation, personas, resilience, observability) — see [docs/architecture/agentic_modules.md](docs/architecture/agentic_modules.md) for the full map. For each core module that is **coherent with the request and would improve the plugin** (capability, robustness, consistency, security, or cost), integrate it instead of rolling your own. The plugin holds only the domain-specific glue; shared machinery comes from `core/`. Document in the PR description which core modules were reused and why any seemingly-relevant one was *not*.
- **Central auth & RBAC integration — mandatory for every new plugin from now on.** The `auth` plugin is the ecosystem's single source of truth for identity, roles, permissions, groups, and per-plugin-tab access. Every new plugin must be *predisposed* for it — no plugin ships its own ad-hoc auth or unguarded surfaces. Concretely:
    - **Declare your tabs.** Implement `get_ui_tabs()` returning one dict per UI surface with a **literal string `id`** (or `self.metadata.name` for a single-surface SPA) and a `label` (English; the UI localizes via i18n). The central tab discovery ([plugins/auth/rbac/discovery.py](plugins/auth/rbac/discovery.py)) and the **Access Control** matrix key access by `(plugin, tab_id)`, so ids must be stable and unique within the plugin. Avoid fully-dynamic tab lists that can't be read statically.
    - **Enforce on the backend.** Protect routes with the shared guards from `plugins.auth.dependencies` — `require_roles(...)` / `require_admin()` (coarse) and the RBAC-aware `require_permission(*slugs)` / `require_tab(plugin, tab)` (granular). Never hand-roll role checks. The central pure-ASGI `PluginAccessMiddleware` already gates every plugin route at plugin level (default-allow, fail-open) from the admin-editable policy; per-sub-tab enforcement inside a multi-tab SPA is the plugin's responsibility.
    - **System / infrastructure plugins set `system: true` in the manifest.** A plugin that is platform machinery rather than a user-facing app (auth itself, and any future infra plugin) declares `system: true` in `manifest.yaml`. The central tab discovery + RBAC service then flip its UI tabs from default-allow to **admin-only** (effective-admin / wildcard) and hide them from the user-facing navigation/catalog — users never see the plugin in their nav, only effective-admins do. This governs **visibility only**: the plugin's *public backend routes* (e.g. a login screen, token refresh) stay reachable, so don't expose a "tab" for an unauthenticated entry screen — gate the screen as a public route and keep tabs for the admin surfaces. Do **not** hand-roll per-user hiding in the plugin UI; set the flag and let the central policy do it. (`auth` is also kept in `PluginAccessMiddleware._UNGATED_PLUGINS` so its login route is never gateway-blocked — system-ness is about nav visibility, route gating remains the plugin's own `require_*` guards.)
    - **Gate the UI centrally.** Plugin frontends consume the shared auth context via the `@auth` alias (`useAuth()` → `canAccessTab(tabId, '<plugin>')`, `hasRole`, `user`); filter internal tabs/actions with it and never reimplement the auth client. The auth UI fetches the central policy (`/api/auth/access/tabs`) once and exposes it to all consumers.
    - **Reuse, don't fork.** Roles, permissions, groups, audit, and the user store live in `auth` — extend the central catalog/policy, do not create a parallel RBAC inside your plugin.
    - **Admin is an *effective* privilege, never a literal role.** Do not gate on `user.has_role(AuthRole.ADMIN)` (or `is_admin()`) alone — `has_role` is a literal enum membership check, but an admin can be provisioned via a **custom RBAC role granted the wildcard (`*`) permission**, in which case the built-in `AuthRole.ADMIN` is absent from `user.roles` (unknown role strings are dropped when the token is decoded). Such a user passes every central gate (`require_permission`, `PluginAccessMiddleware`) yet, under a literal check, is silently misread as an ordinary user inside your plugin — losing admin-only data/actions while still *appearing* admin elsewhere. Decide full access the way the central gates do: from the **effective permission set** — `get_rbac_service().effective_permissions(user_id, roles)` ([plugins/auth/rbac/service.py](plugins/auth/rbac/service.py)) + `has_permission(perms, WILDCARD)` ([plugins/auth/rbac/permissions.py](plugins/auth/rbac/permissions.py)), wrapped in a small resilient helper that falls back to the literal role when the RBAC service is unavailable (degrade closed for elevation). Use the same helper for every admin decision in the plugin (route scope, `/me` `is_admin`, mutation guards, UI gating) so they never disagree.
    - **Consuming the shared `@auth` UI is a build-time coupling — respect it.** A consumer's frontend imports `AuthProvider`/`useAuth` from `@auth` and `ProtectedRoute`/login from `@auth/login`, which are path-aliased to the auth plugin's **source** (`../../auth/ui/src/...`). The consumer's `tsc`/`vite` therefore transitively type-check and bundle whatever the auth login flow reaches (e.g. the MFA `QrCode` component and its `qrcode` dep). Consequences to honour: (a) **`plugins/auth/ui` must have its deps installed before building *any* `@auth`-consumer UI** — node resolves auth's transitive deps from auth's own `node_modules`, not the consumer's, so adding them to the consumer does nothing; (b) keep auth's barrel/shared files (`index.ts`, `login.ts`, `components/shared/*`) **lean and explicitly typed**, so a consumer never breaks on a missing transitive dep or implicit `any`; (c) **never reimplement/fork the auth client** — always import via `@auth` / `@auth/login`.
    - This applies from the plugin's first commit. Existing plugins are grandfathered, but any **new** plugin (and any new user-facing surface) must follow it; document the auth/RBAC wiring in the PR description.
- **Multi-tenancy is identity-derived & mandatory for every new plugin.** Any plugin that persists or returns per-user/per-org data must scope **every** read and write to a tenant, and that tenant is resolved from **who is authenticated**, never from a client-supplied header. The mechanism is centralized — do not reinvent it:
    - **The tenant rides the identity.** At login the `auth` plugin embeds a `tenant_id` claim in the access token via `resolve_user_tenant()` ([plugins/auth/tenancy.py](plugins/auth/tenancy.py)) — by default `tenant_id == user_id` (each user gets an isolated personal tenant), or a single shared tenant when `AUTH_TENANT_ID` pins the whole deployment. `core.auth.jwt.verify_token` reads it back into `AuthUser.tenant_id`, and the shared guard chokepoint (`get_current_user` → `require_auth`/`require_roles`/`require_permission`/`require_tab`) binds it to the tenant context var. So inside any guarded route `get_current_tenant_id()` ([core/context.py](core/context.py)) already returns the logged-in user's tenant.
    - **Read the tenant from the context, never the request.** Resolve the active tenant with `core.context.get_current_tenant_id()` (or `AuthUser.tenant_id`). **Never** trust an `X-Tenant-ID` (or similar) header from an authenticated caller to choose the tenant — that is a cross-tenant data-leak (a user could read another tenant by forging the header). A header may at most select a tenant for unauthenticated **service/job** flows, and must never override the tenant an authenticated user resolves to.
    - **Scope the store.** Every persistence call (SQL `WHERE tenant_id = …`, cache/vector namespace, file path) must include the resolved `tenant_id`. Pass it explicitly through the store layer (see how `baselithoptimizeprocess`/`baselith_pitwall` thread `tenant_id` everywhere). Default-deny: a query that forgets the tenant filter is a bug, not a convenience.
    - **`set_tenant_isolation` / strict mode.** Honour `strict_tenant_isolation` — background tasks/workers that act on behalf of a user must `set_tenant_context(...)` before touching tenant-scoped state, so they never silently fall back to `"default"`.
    - **Per-plugin tenancy mode (`tenancy: shared|personal`).** A plugin's tenancy model is *declarative*, set once in its `manifest.yaml` (`PluginMetadata.tenancy`), not hand-rolled per query. `shared` (default) scopes data by the **deployment-derived** tenant (`get_current_tenant_id()` — pinned / org-membership / per-user, whatever the deploy resolves). `personal` forces **1 user = 1 tenant** *regardless* of how the deployment resolves tenancy, so a per-user surface stays isolated even on a shared/org deploy. The plugin's store must resolve its scope key via `self.tenant_key()` (= `core.context.resolve_plugin_tenant(self.metadata.tenancy)`) instead of calling `get_current_tenant_id()` directly — this stays identity-derived (the per-user key comes from the bound user context, set at the same auth chokepoints as the tenant; `core.context.get_current_user_id()`), never a client header. It degrades safely (falls back to the session/default tenant when no user is bound, e.g. background tasks/scripts). Choose `personal` for private per-user data (notes, chat history, personal vault); leave `shared` for org/collaborative data. Note infra/security-ops plugins are governed by `system: true` (admin-only), **not** per-tenant isolation.
    - **Every new plugin must be *predisposed* to be tenant-aware under BOTH modes (`personal` AND `shared`) — design for it from day one, regardless of the manifest default.** The declared mode is only a default: an admin can flip it at runtime from the auth console ([plugins/auth/admin_router/_plugins.py](plugins/auth/admin_router/_plugins.py)), so the plugin's storage must give a *correct, isolated* result under whichever mode is effective — never assume one. Concretely:
        - **Always resolve the scope key through the framework seam, never `get_current_tenant_id()` directly.** Inside a `Plugin` method use `self.tenant_key()`; in store-layer code that has no `self` (repositories, free functions), use `core.context.resolve_plugin_tenant_key("<plugin-name>", "<declared>")` (the store-layer counterpart — for `shared` with no override it equals `get_tenant_or_default()`, so swapping it in is behaviour-preserving). Both honour a runtime override; calling `get_current_tenant_id()` directly does **not** and silently ignores `personal`.
        - **Scope *every* read AND write by that key** (SQL `WHERE tenant_id = …`, cache/vector namespace, on-disk path, e.g. `vault_root/<key>/…`). A query that forgets it leaks across tenants.
        - **Sub-app-mount plugins (`app.mount(...)`) bypass the host auth dependency chain, so they get NO bound identity by default — `personal` would silently collapse to the shared default vault.** They must (a) add a small pure-ASGI bridge that decodes the central `Authorization: Bearer` via `core.auth.manager.get_auth_manager().authenticate(...)` and calls `set_user_context`/`set_tenant_context` (additive: pass anonymous requests through unchanged — see [plugins/baselithbrain/backend/context_bridge.py](plugins/baselithbrain/backend/context_bridge.py)), **and** (b) make the plugin's own SPA send that token on every request — read it from `localStorage['auth_access_token']` (the single key the `@auth` client writes) and set `Authorization: Bearer …`. A backend that scopes correctly is inert if the frontend never authenticates. Normal `RouterPlugin` routes guarded by the shared `require_*` deps already get the context bound — no bridge needed there. **Gotcha that silently defeats the bridge: a Starlette `Mount` sets `scope["root_path"]` but does NOT strip the prefix from `scope["path"]` — a sub-app mounted at `/foo` sees `scope["path"] == "/foo/api/…"`, not `/api/…`.** Any path-based gate inside the bridge must strip `root_path` first (`rel = path[len(root):]`), or the gate never matches and the bridge no-ops for every request. Verify with a real mounted request, not a direct `TestClient(subapp)` call (the latter has an empty `root_path`, so it passes even while the mounted path is broken).
        - **Verify isolation end-to-end, not just in unit tests with an unauthenticated `TestClient`** (those never exercise the token→bind→scope path): confirm two different users get two different scope keys and anonymous/background falls back to the bare default.
        - Single-owner/config-pinned plugins (one deployment = one owner, e.g. a personal WhatsApp twin) and `system: true` infra/security-ops plugins are the only exemptions — state which, and why, in the PR.
